TCP流量控制与拥塞控制

核心术语

引入：为什么需要流量控制和拥塞控制？

在上一个课题中，我们学习了TCP如何通过三次握手建立连接、通过序列号和确认号保证可靠传输。但仅仅保证可靠性是不够的——如果发送方不顾接收方的处理能力，一股脑地发送大量数据，接收方的缓冲区就会溢出，导致数据丢失。同样，如果发送方不顾网络的承载能力，大量数据涌入网络，就会造成网络拥塞，导致大面积的丢包和延迟。

TCP的解决方案是两个独立但相关的控制机制：流量控制和拥塞控制。流量控制解决的是"发送方和接收方之间的速度匹配"问题，拥塞控制解决的是"发送方和网络之间的速度匹配"问题。

滑动窗口机制

TCP使用滑动窗口（Sliding Window）机制来控制数据的发送。窗口是一个连续的序列号范围，落在窗口内的数据可以被发送而无需等待确认。

发送窗口的大小取决于两个因素中较小的一个：

  • 接收窗口（rwnd）：接收方通告的窗口大小，表示接收方缓冲区还能容纳多少数据
  • 拥塞窗口（cwnd）：发送方根据网络拥塞程度自行维护的窗口大小

实际发送窗口大小 = min(rwnd, cwnd)

窗口的左边界随着已确认的数据向右移动，右边界根据窗口大小相应调整，这就是"滑动"的含义。

流量控制

流量控制的目的是防止发送方发送数据过快，导致接收方缓冲区溢出。接收方通过TCP首部中的"窗口大小"字段，告诉发送方自己还能接收多少数据。

工作过程如下：

  1. 连接建立时，双方通过SYN报文交换初始窗口大小
  2. 数据传输过程中，接收方在每个ACK报文中通告当前的接收窗口大小
  3. 发送方根据接收方通告的窗口大小调整自己的发送量
  4. 如果接收方通告窗口大小为0，发送方必须停止发送数据

当接收方缓冲区满了（窗口为0）时，发送方会启动一个持续定时器（Persist Timer），定期发送窗口探测报文，询问接收方是否恢复了接收能力。这避免了"死锁"——如果接收方发送的"窗口更新"报文丢失，双方就会永远等待。

拥塞控制概述

流量控制处理的是端到端的问题，而拥塞控制处理的是全局性的问题。当网络中的数据量超过网络的处理能力时，就会发生拥塞。拥塞的表现是：路由器队列溢出导致丢包，延迟急剧增加，吞吐量下降。

TCP的拥塞控制基于一个核心原则：发送方根据网络的拥塞程度动态调整发送速率。拥塞程度通过丢包事件来推断——如果发生超时或收到重复ACK，说明网络可能发生了拥塞。

TCP维护一个拥塞窗口（cwnd），初始值通常为1个MSS（最大报文段长度）。拥塞控制算法通过调整cwnd来控制发送速率。

慢启动

慢启动（Slow Start）是TCP连接刚建立或检测到拥塞后恢复时的阶段。虽然叫"慢"启动，但实际上增长速度很快——指数增长。

慢启动的过程：

  1. 连接建立后，cwnd初始化为1个MSS
  2. 每收到一个ACK，cwnd增加1个MSS（也就是说，每经过一个RTT，cwnd翻倍）
  3. 当cwnd达到慢启动阈值（ssthresh）时，转入拥塞避免阶段

例如：cwnd=1 → 发送1个MSS → 收到ACK → cwnd=2 → 发送2个MSS → 收到2个ACK → cwnd=4 → 发送4个MSS → ...

如果发生超时：ssthresh = cwnd/2，cwnd重新设为1，重新进入慢启动。

拥塞避免

当cwnd达到ssthresh后，TCP进入拥塞避免（Congestion Avoidance）阶段。在这个阶段，cwnd的增长从指数变为线性——每个RTT增加1个MSS。

拥塞避免的过程：

  1. 每收到一个ACK，cwnd增加 MSS * (MSS/cwnd)
  2. 每经过一个RTT，cwnd大约增加1个MSS
  3. 如果检测到拥塞（超时或重复ACK），执行相应的处理

这种线性增长是一种"谨慎试探"——TCP不确定网络还能承受多少流量，所以慢慢增加。

快重传与快恢复

当发送方连续收到3个重复ACK时，说明网络中可能有报文段丢失了（但后续的报文段到达了，否则不会有重复ACK）。这时候有两种处理方式：

快重传（Fast Retransmit）：立即重传可能丢失的报文段，而不等待超时。这比超时重传快得多。

快恢复（Fast Recovery）：在快重传之后，TCP Reno和TCP NewReno使用快恢复算法：

  1. ssthresh = cwnd/2
  2. cwnd = ssthresh + 3（加3是因为收到了3个重复ACK，说明有3个数据包离开了网络）
  3. 每收到一个重复ACK，cwnd增加1个MSS
  4. 收到新的ACK后，cwnd设为ssthresh，进入拥塞避免阶段

如果没有快恢复，TCP会像超时一样回到慢启动，这会导致发送速率急剧下降，影响性能。

TCP拥塞控制算法的演进

TCP拥塞控制算法经历了多次演进：

  • TCP Tahoe（1988）：包含慢启动、拥塞避免和快重传。检测到拥塞后，无论是超时还是3个重复ACK，都回到慢启动。
  • TCP Reno（1990）：在Tahoe基础上增加了快恢复。3个重复ACK触发快重传+快恢复，只有超时才回到慢启动。
  • TCP NewReno（1999）：改进了Reno在多个报文段丢失时的性能。
  • TCP SACK（选择性确认）：允许接收方告知发送方哪些报文段已收到，哪些缺失，使发送方可以精确重传。
  • TCP CUBIC（2008）：Linux默认算法，使用三次函数来调整cwnd，在高带宽延迟积网络中表现更好。

RTT与超时计算

TCP的超时时间（RTO，Retransmission Timeout）是根据往返时间（RTT）动态计算的。如果RTO太小，会导致不必要的重传；如果太大，丢失的报文段要等很久才会被重传。

TCP使用Jacobson/Karels算法来计算RTO：

  1. 测量每个报文段的RTT样本
  2. 计算加权移动平均：SRTT = (1-a) * SRTT + a * RTT（a通常取1/8）
  3. 计算RTT偏差：RTTVAR = (1-b) * RTTVAR + b * |SRTT - RTT|（b通常取1/4）
  4. RTO = SRTT + 4 * RTTVAR

这种平滑算法可以避免单个异常RTT样本对RTO的影响。

总结

TCP的流量控制和拥塞控制是保证网络高效运行的关键机制。流量控制通过接收窗口防止接收方缓冲区溢出，拥塞控制通过拥塞窗口防止网络过载。慢启动、拥塞避免、快重传、快恢复这四个算法协同工作，使TCP能够在不同网络条件下自适应地调整发送速率。

理解这些机制对于网络性能调优和故障排查非常重要。例如，如果发现TCP连接的吞吐量很低，可能需要检查窗口大小设置、网络拥塞状况或拥塞控制算法的选择。

练习题

1. TCP实际发送窗口大小由什么决定？

答案：C

解析：TCP的实际发送窗口大小 = min(rwnd, cwnd)。接收窗口防止接收方溢出，拥塞窗口防止网络过载，取较小值以同时满足两个约束。

2. TCP慢启动阶段，每经过一个RTT，拥塞窗口cwnd变为原来的_____倍。

答案：2

解析：慢启动阶段，每收到一个ACK，cwnd增加1个MSS。一个RTT内发送的数据都能收到ACK，所以cwnd翻倍，呈指数增长。

3. 当发送方连续收到3个重复ACK时，TCP会执行什么操作？

答案：B

解析：收到3个重复ACK说明可能有报文段丢失，但后续报文段已到达。TCP执行快重传，立即重传可能丢失的报文段，而不等待超时。

4. 简述TCP慢启动和拥塞避免的区别。

答案：慢启动阶段cwnd指数增长（每RTT翻倍），用于快速探测可用带宽；拥塞避免阶段cwnd线性增长（每RTT增加1个MSS），用于谨慎试探网络容量。当cwnd达到ssthresh时从慢启动转入拥塞避免。

解析：慢启动是"快跑"，快速利用空闲带宽；拥塞避免是"慢走"，避免突然注入大量数据造成拥塞。两者通过ssthresh阈值切换。

5. TCP Reno在检测到超时后，cwnd会如何变化？

答案：C

解析：超时说明网络严重拥塞，TCP Reno将ssthresh设为cwnd/2，cwnd重新设为1个MSS，从慢启动阶段重新开始。
